\section{Introduction and Learning Objectives}
% ============================================================

This report covers the deployment of the Orders4U Spring Boot application to a cloud hosting platform. The original assignment calls for Oracle Cloud Infrastructure (OCI), but I ran into a hard block during OCI account creation. The signup page returned a ``Forbidden'' error on the payment-verification step no matter what I tried. After reaching out to Professor Sluiter, I was approved to use \textbf{Render.com} as an equivalent deployment target.

Render is a PaaS provider, so it skips the manual VCN/subnet/firewall setup that OCI requires. That said, the core learning outcomes are the same: containerise a Spring Boot app with Docker, connect it to a managed MySQL database in the cloud, inject credentials through environment variables, and verify the whole stack is working live.

\subsection{Learning Objectives Achieved}

\begin{itemize}[nosep]
  \item Compare Oracle Cloud's IaaS approach to the PaaS model used by Render, AWS, GCP, and Azure.
  \item Build and containerise a Spring Boot application using Docker and deploy it to a cloud service.
  \item Provision and connect to a managed MySQL database from a cloud-hosted container.
  \item Configure environment variables for secure, externalised database credentials.
  \item Diagnose and fix deployment issues (health-check failures, port binding, datasource overrides).
  \item Evaluate the trade-offs of IaaS vs.\ PaaS deployment in cloud architecture.
\end{itemize}

\section{IaaS vs.\ PaaS: Why Render Instead of OCI}
% ============================================================

\subsection{Oracle Cloud's IaaS Approach}

OCI sits closer to Infrastructure-as-a-Service than the other major providers. Before you can deploy anything, you have to manually set up a Virtual Cloud Network (VCN), configure public and private subnets, add an Internet Gateway, define route tables, and write Security List ingress/egress rules. Only after all that infrastructure is in place can you provision a Compute VM, Container Instance, or MySQL Database Service.

\subsection{Render's PaaS Approach}

Render abstracts the entire networking layer away. Deploying a Docker container takes three things:

\begin{enumerate}[nosep]
  \item A GitHub repository with a \texttt{Dockerfile}.
  \item A Web Service resource on the Render dashboard.
  \item Environment variables for the datasource.
\end{enumerate}

TLS termination, DNS, load balancing, and health checking are all handled automatically. Coming from the Google Cloud Run deployment in Activity~6, this felt very familiar. Both are container-based PaaS platforms where you push code and let the platform handle the rest.

\subsection{Side-by-Side Comparison}

\begin{center}
\begin{tabularx}{\textwidth}{lXX}
\toprule
\textbf{Aspect} & \textbf{OCI (IaaS)} & \textbf{Render (PaaS)} \\
\midrule
Network Setup         & Manual VCN, subnets, gateways, route tables & Fully managed; none required \\
Database              & Oracle MySQL Database Service (private subnet) & External MySQL (Railway) \\
Container Hosting     & OCI Container Instances / OCIR                 & Render Web Service (Docker) \\
Firewall Rules        & Manual Security List ingress/egress             & Automatic; outbound open by default \\
TLS / HTTPS           & Manual certificate or Load Balancer             & Automatic via \texttt{*.onrender.com} \\
Cost (free tier)      & Always-Free shapes available                    & Free Web Service (750\,h/month) \\
Deployment Complexity & High (hands-on DevOps)                          & Low (git-push or image deploy) \\
\bottomrule
\end{tabularx}
\end{center}

I went with Railway (\url{https://railway.app}) because it has a free tier, supports MySQL, and lets you sign in with GitHub. The whole setup took about 30 seconds: \textbf{New Project $\rightarrow$ Database $\rightarrow$ MySQL}, and Railway generated a public hostname, port, username, and password.

\subsection{Schema Initialisation}

The application uses Spring Data JDBC rather than JPA/Hibernate, so it does not auto-create tables on startup. I connected to the Railway database using MySQL Workbench (public host \texttt{interchange.proxy.rlwy.net}, port \texttt{20564}) and ran the same schema SQL from the Docker lab:

\begin{lstlisting}[language=SQL,caption={Create USERS and ORDERS tables on Railway}]
CREATE TABLE IF NOT EXISTS USERS (
  id       INT AUTO_INCREMENT PRIMARY KEY,
  username VARCHAR(100) NOT NULL UNIQUE,
  password VARCHAR(255) NOT NULL,
  role     VARCHAR(50)  NOT NULL,
  enabled  BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE TABLE IF NOT EXISTS ORDERS (
  ID           INT AUTO_INCREMENT PRIMARY KEY,
  ORDER_NUMBER VARCHAR(100),
  PRODUCT_NAME VARCHAR(255),
  PRICE        INT,
  QTY          INT
);
\end{lstlisting}

\section{Application Configuration for Render}
% ============================================================

\subsection{Dockerfile}

The multi-stage Dockerfile builds the JAR inside an Alpine JDK container and copies it into a lightweight JRE runtime image. I added \texttt{chmod +x ./mvnw} because the Maven wrapper lost its execute permission in Git on Windows. Without it, Render's Linux build host fails with ``Permission denied'' (the same issue I hit during the Google Cloud Build in Activity~6).

\begin{lstlisting}[caption={Dockerfile (project root)}]
FROM eclipse-temurin:17-jdk-alpine AS build
WORKDIR /app
COPY . .
RUN chmod +x ./mvnw && ./mvnw package -DskipTests

FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
\end{lstlisting}

\subsection{application.properties: Runtime Overrides}

The same \texttt{\$\{VAR:default\}} pattern from every previous deployment. Every database setting can be overridden at runtime through environment variables without rebuilding the image:

\begin{lstlisting}[caption={application.properties (key lines)}]
server.port=${PORT:8080}

spring.datasource.url=${SPRING_DATASOURCE_URL:jdbc:mysql://...}
spring.datasource.username=${SPRING_DATASOURCE_USERNAME:admin}
spring.datasource.password=${SPRING_DATASOURCE_PASSWORD:...}
spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver

spring.jpa.hibernate.ddl-auto=${SPRING_JPA_HIBERNATE_DDL_AUTO:update}

management.endpoints.web.exposure.include=health
management.endpoint.health.probes.enabled=true
\end{lstlisting}

The last two lines are new. They expose the Spring Boot Actuator health endpoint so Render's HTTP health probe can check if the app is alive without needing to authenticate.

\subsection{SecurityConfig: Permit Health Check}

By default, Spring Security requires authentication on every route. Render's health check hits \texttt{/actuator/health} and expects an HTTP 200. If it gets a 302 redirect to the login page instead, Render thinks the app is down and kills it. I added \texttt{/actuator/health} to the permit list:

\begin{lstlisting}[language=Java,caption={SecurityConfig.java: health-check permit}]
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/actuator/health", "/actuator/health/**")
        .permitAll()
    .requestMatchers("/users/register", "/users/processRegister",
                     "/users/login").permitAll()
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .anyRequest().authenticated()
)
\end{lstlisting}

\section{Collaborating with AI}
% ============================================================

\subsection{3A: Cross-Cloud Reflection}

\textbf{Prompt:} ``How does deploying a Java application with MySQL on Oracle Cloud compare to similar workflows on AWS (Aurora + ECS), Azure (Database for MySQL + Container Instances), or Google Cloud (SQL + Cloud Run)? Which platform might best suit different project priorities such as cost, performance, or ease of use?''

\textbf{Summary of Findings:}

AWS has Aurora and ECS Fargate which is powerful but honestly overkill for a project like this, and the free tier only lasts 12 months. Azure works well if you already use Microsoft stuff since it ties into Active Directory, but otherwise it felt like extra steps for no real benefit. Google Cloud was probably the easiest of the big three --- Cloud Run scales to zero so you don't pay when nothing is running, and I got to see that in Activity~6. OCI wants you to configure everything yourself which gives you control but it took forever compared to the others.

I've now deployed this same Orders app on AWS (Activity~5), Google Cloud (Activity~6), Azure (Activity~3), and Render (Activity~8). The app code never changed between any of them, just the infrastructure around it. I normally use Vercel for my own stuff and I love it, but it's really made for frontend and Node apps, not Java. For this Spring Boot project Render was by far the easiest. You just point it at a repo with a Dockerfile, add a few environment variables, and you're done. No VCN, no socket factories, none of the extra setup the other platforms needed.
