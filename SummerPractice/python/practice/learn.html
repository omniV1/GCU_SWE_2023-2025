4. Pattern 1 — Map & Reduce

From 01_richest_customer.py

The shape

You have a collection of things. For each thing, compute a number. Then reduce all those numbers into a single answer (max, min, sum, count).

collection ---map--->  [n1, n2, n3, ...]  ---reduce--->  answer

Your solution

def maximumWealth(accounts):
    return max(sum(customer) for customer in accounts)
What you nailed: generator expression instead of building a list, single line, reads like English. This is genuinely idiomatic Python.

Quiz

Q1. What is the time complexity of max(sum(row) for row in accounts) when accounts has m rows and n columns?
O(m × n). Outer iteration is m rows; inside, sum(row) walks all n elements of that row. Multiply.
Q2. What's the difference between [sum(r) for r in rows] and (sum(r) for r in rows)?
Memory. For max(...), max only needs one value at a time, so the generator is the right tool — O(1) extra space instead of O(m).

5. Pattern 2 — Running state, single pass

From 02_max_consecutive_ones.py UNSOLVED

The shape

Walk an array once. Carry two pieces of state with you: what's true right now, and the best you've ever seen. Update both as you walk.

Why this matters

Beginners reach for "compute all the runs first, then take the max." That's two passes and a list. The streaming version is one pass and one integer. Same answer, infinitely better for large inputs (think: server logs, sensor data).

The solution, built step by step

def findMaxConsecutiveOnes(nums):
    current = 0      # length of the run I'm in RIGHT NOW
    best    = 0      # longest run I've ever seen

    for n in nums:
        if n == 1:
            current += 1
            best = max(best, current)
        else:
            current = 0

    return best
Why update best inside the if branch? If you only update best when you hit a zero, a list ending in 1's never triggers it. Updating on every 1 is bulletproof — no trailing edge case.

How to recognize this pattern

  • You walk a sequence exactly once (left to right).
  • The answer depends on something you've seen previously — so you carry state.
  • Usually two variables: "current" (the thing happening right now — resets) and "best" (the all-time peak — only updates upward).
  • Keyword cues: "longest run/streak", "max so far", "running total", "most consecutive", "best window ending at i".

PA 2.7 — Select all that apply

Which of these problems are solved by the "running state" pattern?

The deeper lesson — "streaming" thinking

  • Monitoring: max latency in the last hour
  • Finance: longest streak of green days
  • Games: longest combo

You're always tracking "now" and "best." Sometimes "worst." Sometimes "average so far." It's the same skeleton.

Quiz

Q3. You're tempted to skip best = max(best, current) inside the loop and just do return max(...) at the end. Why won't that work without rewriting?
You'd lose history. The whole point of best is to remember peaks that the current state has since moved past. State that you don't snapshot is state you've forgotten.

6. Pattern 3 — Two pointers, converging

From 03_valid_palindrome.py UNSOLVED

The shape

One pointer starts at the left, one at the right. They walk toward each other. The loop ends when they meet.

A

Blue = left pointer. Purple = right pointer. They move inward.

Why this beats "reverse and compare"

The naive solution is: clean the string, reverse it, compare. That works, but allocates two extra strings. Two pointers compare in-place — O(1) extra memory. Same answer, less garbage.

The skeleton you should memorize

def isPalindrome(s):
    left, right = 0, len(s) - 1
    while left < right:
        # 1) skip junk on the left
        while left < right and not s[left].isalnum():
            left += 1
        # 2) skip junk on the right
        while left < right and not s[right].isalnum():
            right -= 1
        # 3) compare
        if s[left].lower() != s[right].lower():
            return False
        left += 1
        right -= 1
    return True
The classic bug: forgetting left < right inside the inner while loops. On the input ".,!?" the left pointer will walk right off the end of the string and crash. Always re-check the bound in nested loops.

Q5. The loop condition is while left < right, not while left <= right. Why?
Once left == right they point to the same character. Any character equals itself. No information gained. Stop.
Q6. What's the time complexity?
Inner whiles look like nested loops but each is amortized linear: across the whole run, left moves right at most n times and right moves left at most n times. Total work ≤ 2n.

7. Pattern 4 — Two pointers, same direction

From 283_move_zeroes.py and 392_Is_Subsequence.py

The shape

Both pointers start at the left. One races ahead (scanner), the other lags behind (writer). The lagging pointer only advances when something interesting happens.

This is one of the most useful patterns in your whole toolkit. Once you see it, you'll see it everywhere — deduplication, filtering, in-place compaction, subsequence checks, sliding windows.

Your Move Zeroes solution

def moveZeroes(self, nums):
    left = 0
    right = 0
    while right < len(nums):
        if nums[right] != 0:
            nums[left], nums[right] = nums[right], nums[left]
            left += 1
        right += 1
    return nums
Excellent. right is the scanner — it looks at every element. left is the writer — it only advances when we keep a value (i.e. it's non-zero). Swapping (instead of just writing) is what guarantees the zeroes end up at the end with no extra space.

Your Is-Subsequence solution

def isSubsequence(self, s, t):
    left = 0
    right = 0
    while left < len(s) and right < len(t):
        if s[left] == t[right]:
            left += 1
        right += 1
    return left == len(s)
Same skeleton, different verbs. right always advances (scan every char of t). left only advances when there's a match (move on to the next char we still need to find).

How to recognize this pattern

  • You need to filter, deduplicate, partition, or match in lockstep — in place if possible.
  • One pointer ("scanner") looks at every element. The other ("writer") only advances when something passes a test.
  • The answer is either the writer's final position (a length / index), or the mutated array itself.
  • Keyword cues: "remove duplicates / element", "move all X to one side", "is X a subsequence of Y", "partition by condition", "compact / squeeze out".

8. Pattern 5 — Greedy with thresholds

From 12_integer_to_roman.py

The shape

"Repeatedly take the biggest chunk that fits, subtract it, repeat." A greedy algorithm. It works for Roman numerals because the system is constructed so the greedy choice is always optimal.

Your solution

Your big if/elif chain is correct. It's also 26 lines of similar-looking code. That's a smell — when code repeats itself, table-drive it.

The same logic, table-driven

def intToRoman(num):
    pairs = [
        (1000, "M"),  (900, "CM"), (500, "D"),  (400, "CD"),
        (100,  "C"),  (90,  "XC"), (50,  "L"),  (40,  "XL"),
        (10,   "X"),  (9,   "IX"), (5,   "V"),  (4,   "IV"),
        (1,    "I"),
    ]
    out = []
    for value, symbol in pairs:
        count, num = divmod(num, value)
        out.append(symbol * count)
    return "".join(out)
Three wins:
  1. Data, not control flow. The Roman numeral rules live in one list. To add a new symbol, edit the data, not the if-chain.
  2. divmod. "How many fit, and what's left?" in one call. Beats while num >= value: ....
  3. join over +=. Building strings with += in a loop is O(n²) in the worst case in most languages; Python optimizes the common case but "".join(list) is the idiomatic, fast version.

When greedy works (and when it doesn't)

Greedy is dangerous: it doesn't always give the optimal answer. Classic example:

ProblemGreedy works?Why
Integer → RomanYesRoman denominations are designed for it.
Coin change with US coins {1,5,10,25}YesStandard coin system.
Coin change with {1, 3, 4} → make 6NoGreedy picks 4+1+1=3 coins. Optimal is 3+3=2 coins.

For untrusted coin sets, you need dynamic programming. That's a future topic — but knowing the limit of greedy is half the lesson.

From 14_longest_common_prefix.py

Your solution

        return ""

Subtle correctness check: what happens when prefix shrinks all the way to ""? "anything".startswith("") is True, so the inner while loop exits cleanly and we eventually return "". The empty string is the universal prefix — your code handles it without a special case. Nice.

The pattern: "candidate, then refute"

Take the first item as a tentative answer. Walk the rest. Every time you find evidence the candidate is too generous, shrink it. If it survives the gauntlet, return it.

This is the same shape as "running minimum," "running max," "candidate winner in a vote," etc. Pick a champion, defend them.

Complexity

Worst case: every string forces the prefix to shrink one character at a time. With n strings of length L, you do up to n × L character comparisons. For typical inputs it's much faster.

An alternative: vertical scan

def longestCommonPrefix_vertical(strs):
    if not strs:
        return ""
    for i, ch in enumerate(strs[0]):
        for s in strs[1:]:
            if i >= len(s) or s[i] != ch:
                return strs[0][:i]
    return strs[0]

Same Big-O. The vertical version often returns earlier on diverse inputs (you fail at the first character that disagrees, before even looking at all the strings). Horizontal is shorter; vertical short-circuits faster. Both are valid — knowing both shows depth.

How to recognize this pattern

  • You have multiple sequences and want to find what they all share.
  • "Candidate, then refute": take a tentative answer, shrink it whenever new evidence disagrees.
  • Keyword cues: "common prefix / suffix", "intersection of arrays", "longest match", "candidate winner" (in election/voting problems).

10. Pattern 7 — Counting & XOR

From 389_find_the_difference.py

Your solution

def findTheDifference(self, s, t):
    xor_val = 0
    for ch in s:
        xor_val ^= ord(ch)
    for ch in t:
        xor_val ^= ord(ch)
    return chr(xor_val)
This is a beautiful piece of code. O(n) time, O(1) space, and zero allocations.

Why XOR works

XOR has three magical properties:

  • a ^ a == 0 — anything XOR'd with itself cancels.
  • a ^ 0 == a — XOR with zero is identity.
  • a ^ b == b ^ a — order doesn't matter (commutative + associative).

So when you XOR every character of s with every character of t, every character that appears the same number of times in both strings cancels itself out. Only the odd one out survives. Magic? No — it's group theory. But it feels like magic.

Three valid approaches, ranked

ApproachTimeSpaceReadability
Sort both, compare char by charO(n log n)O(n)Easy to explain
Counter(t) - Counter(s)O(n)O(n)Most "Pythonic"
XOR (yours)O(n)O(1)Clever, requires bit insight

The Counter version, for your toolkit

from collections import Counter

def findTheDifference(s, t):
    diff = Counter(t) - Counter(s)
    return next(iter(diff))

Counter is a multiset. Subtracting two counters gives you the surplus. Whenever a problem says "what extra / what's missing," reach for Counter.

How to recognize this pattern

  • You need to count occurrences, find duplicates, missing values, extras, or pair things that cancel.
  • Use Counter for general counting; use XOR when items appear in pairs that should cancel.
  • O(n) time, often O(1) space if you can use XOR or a fixed-size array (e.g., 26 letters).
  • Keyword cues: "extra/missing character", "appears once", "find the duplicate", "anagram", "frequency".

11. Pattern 8 — Index-driven iteration bug walkthrough

From 1768_merge_strings_alternatively.py

The intended pattern

Two strings of possibly different lengths. Pick one char from each, alternating, until both are exhausted. Conceptually simple — index by i from 0 to max(len(a), len(b)) and conditionally append each character if that string still has one at that index.

Your current code

class Solution:
    def mergeAlternately(self, word1, word2):
        word3 = ""

        for i in range(max(len(word1), len(word2))):
            if i < len(word1):

                word3 += word1[i]
            if i < len(word2):
                word3 += word2[i]
            else:
                print("Error: word2 is longer than word1")
            return word3
There are three bugs in this file. Let's find them together before showing the fix.
Bug 1 — indentation

return word3 is indented inside the for loop. The function returns after the first iteration, so you only ever merge one character of each word.

Bug 2 — wrong else branch

The else is attached to if i < len(word2). So the message "word2 is longer than word1" actually triggers when word2 ran out, which is the opposite of what it claims. The message should not be there at all — this is a normal, expected condition, not an error.

Bug 3 — concatenation strategy (style/perf)

Building a string with += in a loop works but isn't ideal — each += on a string conceptually creates a new string. Idiomatic Python: build a list of pieces, then "".join(pieces). CPython usually optimizes this case, but you should still build the habit because it's portable and faster on JVM/.NET-style runtimes.

The corrected version

class Solution:
    def mergeAlternately(self, word1, word2):
        out = []
        for i in range(max(len(word1), len(word2))):
            if i < len(word1):
                out.append(word1[i])
            if i < len(word2):
                out.append(word2[i])
        return "".join(out)

Bonus: a one-line version using zip_longest

from itertools import zip_longest

def mergeAlternately(word1, word2):
    return "".join(a + b for a, b in zip_longest(word1, word2, fillvalue=""))
Why this works: zip_longest pairs up the strings, filling the shorter one with "". Each pair contributes "a then b" to the output. Don't write the one-liner version until you can write the explicit one in your sleep — clever code that you don't deeply understand is technical debt.

How to recognize this pattern

  • You're iterating by index, not by element — because you need to coordinate two or more sequences in lockstep.
  • Sequences may have different lengths; you handle the leftover after the shorter one runs out.
  • Common helpers: range(max(len(a), len(b))), zip (truncates), zip_longest (fills).
  • Keyword cues: "merge alternately", "interleave", "combine row-wise", "process in parallel", "shuffle two arrays together".

Worked example — “Minimum drone speed to finish deliveries in H hours”

Real pattern: binary search on answer (Koko / ship packages).

import math

def min_speed(weights, hours):
    def feasible(speed):
        return sum(math.ceil(w / speed) for w in weights) <= hours
    lo, hi = 1, max(weights)
    while lo < hi:
        mid = (lo + hi) // 2
        if feasible(mid):
            hi = mid
        else:
            lo = mid + 1
    return lo

Must say: “feasible(speed) is monotonic — once true for mid, true for all larger speeds.”

Worked example — “Count blocked storage rooms forming islands” 
def count_islands(grid):
    if not grid: return 0
    rows, cols = len(grid), len(grid[0])
    def dfs(r, c):
        if r < 0 or c < 0 or r >= rows or c >= cols or grid[r][c] != "1":
            return
        grid[r][c] = "0"
        for dr, dc in ((1,0),(-1,0),(0,1),(0,-1)):
            dfs(r+dr, c+dc)
    islands = 0
    for r in range(rows):
        for c in range(cols):
            if grid[r][c] == "1":
                islands += 1
                dfs(r, c)
    return islands

20. Bar raiser & follow-ups

The Bar Raiser is usually not on the hiring team. They optimize for long-term Amazon bar and LP depth. They ask “why / how do you know / what would you do differently” until the story cracks.

Follow-ups to prep for EVERY story

  • What was YOUR specific contribution vs the team?
  • What alternatives did you consider?
  • What data / signal changed your mind?
  • Who disagreed? How did you handle it?
  • What failed? What did you learn?
  • If you redid it next quarter, what changes?
  • How did this help the customer / business?
During coding, Bar Raisers also grade: Do you clarify? Do you catch your own bugs? Do you take feedback without ego? Do you state complexity honestly?

OOD / design lite (often shows up for SDE)

Be ready to design a small object model in 20–25 minutes:

  • Parking lot / elevator / library
  • Amazon: package tracking, shopping cart, flash sale inventory, rate limiter

Script: requirements → entities → relationships → core APIs → edge cases (concurrency, failure). Not full distributed design unless you’re interviewing L5+.
